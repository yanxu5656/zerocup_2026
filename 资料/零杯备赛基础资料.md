## 三、比赛主题（三选一）

1. **市井烟火·百味人间** —— 记录平凡日子里的温度与生机（菜市场、老街、深夜烧烤摊等市井百态）。
2. **匠心传成，非遗焕新** —— 用现代网页语言为传统工艺打开新窗口（非遗数字展馆、匠人故事专题、技艺互动体验等）。
3. **长征万里，薪火千秋** —— 红军长征胜利九十周年，在数字时代传承长征精神。

⚠️ 注意区分两个概念（学长姐特别强调）：
- **主题是比赛要求**（必须三选一，贴合主题）；
- **网站类型是实现方式**（完全不限）。手册中的创意网站、门户网站、游戏网站、WIKI 仅为**参考方向**，不是必选赛道。可以做信息服务网站、互动游戏、校园工具、知识型网站或任何有创意的网页产品。
- 评判关注：作品是否符合所选主题、是否有明确创意、完整的使用流程和较好的用户体验。

## 四、必须讲清楚的基本规则

### 4.1 技术规则（红线）

**允许使用：**
- HTML、CSS、JavaScript；
- Vue、React 等工程框架；
- ECharts 等**功能性库**（使用后必须在 README 中注明每一个库及其用途；评选时只看其与整体的协调程度，**不计入制作难度分**）；
- 后端场景可使用现有的后台框架 / 成熟内容管理系统（CMS），须在提交时注明框架及用途。**后端开发本身不计入整体评价**，但前后端协作程度与交互表现是加分项；
- 游戏网站可使用游戏类框架，但**不可使用框架内提供具体功能实现的现成模块和类**。

**禁止使用：**
- **一切预设样式/组件库**，如 Bootstrap、Vue Element（Element Plus）、Ant Design 等。即可以用框架，但不能套现成的页面模板。
- 提交后组委会会**审查代码**判断违规；不确定的库应**提前咨询赛事工作人员**（QQ 群 1026232938）。

### 4.2 界面规格与运行环境

- 界面规格三选一：**1920 / 1440 / 720**（静态网页需满足的宽度规格），作品中须附带说明自己采用的规格；
- 若为**自适应（响应式）**，展示过程中会被随机改变规格 —— 这是**加分项**之一；
- 运行环境：**Chrome 129**；
- 测试环境包含：**正常网速 + 网速过慢**两种场景。

### 4.3 原创要求

- 网页不能基于任何现有作品，不得抄袭；代码审查发现与现有项目重复度极高或其他违规行为，**取消参赛资格**；
- **AI 生成的代码不能成为抄袭的理由**：需理解自己提交的代码、检查素材来源、对最终作品负责。

### 4.4 评分体系（初赛评分细则 · 附件四）

**总分 = 标准分 + 加分项**；零组总分 100 分，壹组总分 110 分。

| 维度  | 分值            | 细分项与档位（由低到高）                                                       |
| --- | ------------- | ------------------------------------------------------------------ |
| 创意  | 10            | 创意与创新（2–10）：上世纪的创意 2 → 中规中矩 4 → 有所创新 6 → 眼前一亮 8 → 创新鬼才 10          |
| 功能  | 20            | 功能丰富性 10；流畅性与实用性 5（反人类 1 → 十分易用 5）；内容充实度 5（不健康 -5 → 丰富多彩 5）        |
| 设计  | 45            | 整体风格与视觉效果 10；布局结构 10；网页细节（交互）10；素材质量 10；跳转与导航 5（只有主页 0 → 想去哪就去哪 5） |
| 文档  | 5             | 没有文档 0 → 简单文档 3 → 清晰完整的代码与设计文档 5                                   |
| 技术  | 零组 20 / 壹组 30 | 技术水平 10/20；适配 10（屏幕 + 浏览器适配，不同尺寸 Chrome/IE 下显示正常无形变缺失）             |
| 加分项 | 每项 +5～10      | **移动端适配**（移动端响应式运行）／**数据后台**（前后端数据交互与持久化），须经技术人员判定有效               |

学长姐提示：**加分项不是无限堆功能**。核心页面没做好，加登录、数据库、后台管理并不会自动变成高分作品；先把一条核心流程做完整、做精致。

### 4.5 README 要求

提交的 README.md 必须包含：
- 组内成员介绍；
- 使用的**非自己编写的库**及各自用途（含后端框架/CMS）；
- 项目补充信息。

## 七、学长姐经验要点（与备赛规划相关）

### 7.1 组队建议（刘畅 & 飞书文档）
- **靠谱比认识更重要**：能稳定投入时间、按分工完成、及时沟通、愿意打磨；
- 组队前问三个问题：想做到什么程度？每周可投入多少时间？想负责产品/设计/开发还是答辩？
- 典型分工参考（2025 壹组一等奖队）：**3 名开发（2 前端 + 1 后端/数据库/AI 工作流）+ 1 名 UI**，队长负责打包提交与路演 PPT，答辩由表达能力强的队员负责；可跨学院招募引入专业 UI；
- 今年 AI 已能完成大量代码生成，"会不会写代码"不再是唯一优势，**更应找有产品感和想法的队友**；
- 一人可兼多角色，但必须明确谁负责什么。

### 7.2 开发流程参考
- UI 用 Figma 画原型图 → 前后端据此从 0 到 1 实现；
- 整体开发周期约**两周**，期间保持高频沟通对齐进度；
- 强烈建议用 **Git/GitHub** 托管代码，不要用 QQ 传文件；
- 初学者可在 GitHub 借鉴开源项目学习，但**正式比赛必须独立从 0 到 1 搭建**（手册原创要求）。

### 7.3 AI Coding 使用规范（与比赛规则直接相关）
- 在 AI 全局提示词中**强制声明禁用** Bootstrap、Element Plus、Vue Element、Ant Design 等预设样式/组件库，防止 AI 自动引入违规依赖；
- 不要把登录、聊天、支付、后台管理等复杂功能当亮点，比赛更看重核心流程完整与作品完成度；
- **不要直接提交 AI 第一次生成的代码**：至少完成本地运行、页面点击测试、窄屏测试、慢速网络测试、控制台报错检查、依赖与第三方库检查、README 检查；
- 好提示词六要素：角色 + 背景 + 目标 + 约束 + 输出格式 + 验收标准；一次只让 AI 开发一个页面。
